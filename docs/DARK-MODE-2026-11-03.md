# Dark mode, stages 0 and 1: notes for review

The owner asked for what a site opens in to become a setting. Stage 2 is further down.
Stages 3, 4 and 5 are further down. That is the whole plan. Stage 4 went live with no second review, because
the other agent was out of quota: it is still owed, along with stage 5.

## What changed

- `schema.colorMode.start`: `light`, `dark` or `system`. Absent until the owner chooses,
  so existing sites store and render as before. `followDevice` is still written, derived
  from `start`, for tabs running the previous version. Such a tab drops `start` if the
  owner edits a palette colour there.
- `colorModeFor` turns `start` into the fields the head script and `ColorModeRoot` already
  read: `initial` for light and dark, `followDevice` for system. Opening in the designed
  palette with no switch still returns null: one palette, same output.
- The Theme panel has a radio group in place of the device checkbox.
- `color-scheme` follows the palette on the page. It is left out of HTML block documents,
  and frames on the page are set to `normal`.
- Without storage, a press now always writes `?pwb-theme=`, also when it returns to the
  designed palette. Otherwise a reload on a site that opens in the other palette, or on the
  device, undid the choice. Links carry the palette only when the address holds a choice.
- With storage, a press removes an old `?pwb-theme=`, which would outrank the new choice.
- The responsive writer puts the palette after its own `:root`, which used to win.
- `page_fingerprint` includes whether the site has a switch, only when it does. A switch
  gives every page both palettes, so adding or removing one must turn the other pages blue.
  **Sites that already have a switch show all their files blue once after this deploys.**

## Checked by running

Local Chromium on `/s/`, site with no switch and `start: dark`: opens dark on both pages.
An HTML block's corner pixel is `rgb(17,19,23)`, the same as the page; with the frame rule
taken away it is white, so the rule is what prevents the white box.

## Known limits

- Form controls inside an HTML block stay light: a block document cannot declare a scheme
  without the white box.
- No `<meta name="color-scheme">`: the CSS is inline in the head and applies before the
  first paint, so it adds nothing.
- `/site/<slug>` decides from the live pages alone, so a switch on a page that is not live
  does not count there, while `/s/` documents were written from the whole draft.

## Stage 2: a visitor's choice on `/s/` across visits

The sandbox leaves the page no storage and no readable cookie, so the server keeps the choice.

- An address with `?pwb-theme=light|dark` is answered with a cookie: `Path=/s/<slug>/`,
  `HttpOnly`, `SameSite=Lax`, one year. A later visit gets `data-pwb-chosen` on the palette
  script, which the head script reads after the address and storage and before the owner's
  `start`. Only a document with both palettes is touched; any other is served as before.
- `Vary: Cookie` is required, and the spec shows why: without it the browser's 60 second copy
  of the first visit wins and the choice seems lost. A page that sets or reads the cookie is
  `Cache-Control: private`.
- Links also carry the choice on `auxclick` and `contextmenu`, so a middle click or "open in
  new tab" has it (checked by hand in Chromium, middle click only).

Limits:

- A visitor who presses the switch and leaves without any navigation or reload writes no cookie.
  A single-page site keeps the choice only until the tab closes, unless it is reloaded.
- Documents written before this have a head script that does not read `data-pwb-chosen`. They
  gain the memory the next time they are sent live.
- Safari is not checked: CI runs Chromium and Firefox.
- A shared link with `?pwb-theme=` sets that palette for the person who opens it, on that site.

## Stage 3: the device as a choice, and a switch on every page

- A visitor's choice is now `light`, `dark` or `system`, in the address, storage and the cookie.
  `system` outranks the owner's `start`. The head script writes `data-pwb-theme` (the palette),
  `data-pwb-theme-pick` (the choice) and `data-pwb-theme-follow` (it comes from the device).
- `states: 'three'` makes the block a radio group with its own names. It is absent until chosen, so
  a two-way switch stores what it did and its pages stay green. `data-pwb-theme-toggle="choices"`
  keeps it counted as the site's switch on both sides.
- A page on the device follows a device change while open: the runtime, and `ColorModeRoot` in the app.
- Theme panel: "Add one to {count} pages", for canvas pages, as one undo step that leaves the page on
  screen and the selection. A switch added for the owner goes in the top right
  corner, under a bar across the top. `addComponent`'s body is now `insertComponent`, unchanged.

Limits:

- It is not placed inside the navigation bar, only under it, and an HTML page still gets its own
  from Components.
- On the canvas no choice is highlighted: there is no visitor there.
- Documents already live have the old head script, which does not read `system`. A visitor can only
  get `system` from a page written with the new runtime, but an address carrying it to an old page
  opens that page as the owner chose.

## After the review of stage 3

All four points held when checked:

- The viewer's choice crossed from one `/site/<slug>` to the next. Reproduced with a route change; no
  link in the app makes that move today, so it is reached rarely, but the page does stay mounted.
- `ColorModeRoot` read what a page opens in only once. It now keeps only what the visitor chose, and
  follows the rest. A page also started with no palette if the site gained its second one while open.
- On a page that flows, the switch went to the end. It now goes to the top, under a bar there, also
  from "Add a theme switch to this page".
- "Add one to every page" did not reach HTML pages. The button now says how many pages it reaches,
  and the panel says why an HTML page is not among them.

## The device on a first load in Firefox

An earlier version of this note said Playwright's Firefox tells a page about the device only after its
first scripts. The third review disproved that: on synthetic pages Firefox reads dark from the first
script; on a real `/s/` page it reads light even after load. Do not rely on that explanation.

What is known:

- Real `/s/` responses carry `Cross-Origin-Opener-Policy: same-origin`, from Django's default. The
  review's synthetic pages did not. The browser probe measured that one difference over a real
  connection, in CI run 41683603553, with `colorScheme: 'dark'`. Firefox 155: dark without the header,
  light with it. Chromium: dark both ways. That the emulation is lost when Firefox moves the page to a
  new browsing context is the likely mechanism, not something measured.
  That measuring test was removed once it had answered: it timed out in Firefox on a later run, and it
  guarded nothing of ours.
- Under that same real page and header, Firefox with a real device preference opens dark, on the first
  request and on a reload (the guard below, same run).
- System Firefox 159 with no Playwright, a real published page at `?pwb-theme=system`, and
  `ui.systemUsesDarkTheme` set in the profile: dark with it on, white with it off. A one-off check.
- The first-load guard in `dark-mode-published-review.spec.js` runs in both browsers. In Firefox it
  sets a real device preference at launch instead of the emulation.

Safari is still unchecked.

## Stage 4: more colours follow, and a warning when they cannot be read

- `rgb()`, `hsl()`, 4 and 8 digit hex and named greys now follow the palette, wherever hex did.
  `parseColor` reads them. A named colour with a hue stays the owner's own.
- A colour with an opacity keeps it: `color-mix(in srgb, var(--pwb-alt-x, #hex) N%, transparent)`.
  `color-mix` has been in browsers since 2023; in an older one that declaration is dropped.
- A background under 50% opacity is a tint: it no longer counts as the owner's colour, so the text on
  it follows the palette. This changes what a page does in the other palette when it is sent again.
- Tab row colours follow, and an active tab's text follows its own background.
- `style='...'` in single quotes, and an HTML page's palette written in rgb, are read.
- Theme panel: a warning under a colour that falls short of 4.5:1 for text, 3:1 for a brand colour.
- The suggested button text now picks a colour that reaches 4.5:1. The warning found this: the old
  brightness rule left 10 of the 25 presets at 3.2 to 4.4. Pages get it when they are sent again.
- An HTML page can show the other palette in View before it has a switch.

Limits:

- Still not followed: `box-shadow`, SVG `fill` and `stroke` attributes, external stylesheets, `customCss`,
  colours set by a page's script, and the HTML block's tweak colours.
- A stylesheet does not say what a white box is, so it reads as the page background rather than a card.
- The code-project mode's View does not show the other palette.
- The warning checks the other palette only, on seven pairs, not each block's real colours.

## Stage 5: an image for each palette, the browser bar, and HTML blocks

- An image can have `srcOther`, the version for the palette the page is not designed in. It is absent until
  added, so what an image stores does not change. On a site with one palette it is not written at all.
- Writers put two `<img>` in the page, classed `pwb-on-light` and `pwb-on-dark`, and CSS shows one. The other
  one has `loading="lazy"`. The in-app renderer changes `src` instead. HTML pages keep their own images.
- `<meta name="theme-color">`, where the page set one, takes the other palette's background and goes back.
- An HTML block used to show its designed palette first. Measured with a Chromium screencast on a published
  page at `?pwb-theme=dark`: in 3 of 8 loads the block was white on the dark page. Now a page opening in the
  palette it is not designed in holds `iframe[srcdoc]` back until the block has been told: on its load, or the
  page's. A CSS animation shows it after 3 seconds if the runtime never came. Measured again: 0 of 8.

Limits:

- A page opening in its other palette downloads both images when the first is the hidden one.
- A lazy block scrolled into view later can still show its designed palette first.
- The in-app viewer's frames are not held back.
- The navigation bar's logo has no version for the other palette.
- The Image panel always shows the second image's field, also on a site with one palette.
- Firefox and Safari were not measured for the flash; the hold is plain CSS and the e2e spec checks the release.
