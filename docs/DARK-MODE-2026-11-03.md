# Dark mode, stages 0 and 1: notes for review

The owner asked for what a site opens in to become a setting. Stage 2 is further down.
Stages 3 to 5 of the plan (three-state switch, wider colour coverage, per-mode images) are
not started.

## What changed

- `schema.colorMode.start`: `light`, `dark` or `system`. Absent until the owner chooses,
  so existing sites store and render as before. `followDevice` is still written, derived
  from `start`, for tabs running the previous version. Such a tab drops `start` if the
  owner edits a palette colour there.
- `colorModeFor` turns `start` into the fields the head script and `ColorModeRoot` already
  read: `initial` for light and dark, `followDevice` for system. Opening in the designed
  palette with no switch still returns null: one palette, same output.
- The Theme panel has a radio group in place of the device checkbox.
- `color-scheme` follows the palette on the page. It is left out of HTML block documents,
  and frames on the page are set to `normal`.
- Without storage, a press now always writes `?pwb-theme=`, also when it returns to the
  designed palette. Otherwise a reload on a site that opens in the other palette, or on the
  device, undid the choice. Links carry the palette only when the address holds a choice.
- With storage, a press removes an old `?pwb-theme=`, which would outrank the new choice.
- The responsive writer puts the palette after its own `:root`, which used to win.
- `page_fingerprint` includes whether the site has a switch, only when it does. A switch
  gives every page both palettes, so adding or removing one must turn the other pages blue.
  **Sites that already have a switch show all their files blue once after this deploys.**

## Checked by running

Local Chromium on `/s/`, site with no switch and `start: dark`: opens dark on both pages.
An HTML block's corner pixel is `rgb(17,19,23)`, the same as the page; with the frame rule
taken away it is white, so the rule is what prevents the white box.

## Known limits

- Form controls inside an HTML block stay light: a block document cannot declare a scheme
  without the white box.
- No `<meta name="color-scheme">`: the CSS is inline in the head and applies before the
  first paint, so it adds nothing.
- `/site/<slug>` decides from the live pages alone, so a switch on a page that is not live
  does not count there, while `/s/` documents were written from the whole draft.

## Stage 2: a visitor's choice on `/s/` across visits

The sandbox leaves the page no storage and no readable cookie, so the server keeps the choice.

- An address with `?pwb-theme=light|dark` is answered with a cookie: `Path=/s/<slug>/`,
  `HttpOnly`, `SameSite=Lax`, one year. A later visit gets `data-pwb-chosen` on the palette
  script, which the head script reads after the address and storage and before the owner's
  `start`. Only a document with both palettes is touched; any other is served as before.
- `Vary: Cookie` is required, and the spec shows why: without it the browser's 60 second copy
  of the first visit wins and the choice seems lost. A page that sets or reads the cookie is
  `Cache-Control: private`.
- Links also carry the choice on `auxclick` and `contextmenu`, so a middle click or "open in
  new tab" has it (checked by hand in Chromium, middle click only).

Limits:

- A visitor who presses the switch and leaves without any navigation or reload writes no cookie.
  A single-page site keeps the choice only until the tab closes, unless it is reloaded.
- Documents written before this have a head script that does not read `data-pwb-chosen`. They
  gain the memory the next time they are sent live.
- Safari is not checked: CI runs Chromium and Firefox.
- A shared link with `?pwb-theme=` sets that palette for the person who opens it, on that site.

## After the review (`DARK-MODE-REVIEW-2026-11-03.md`)

All four findings held when checked, and are fixed or covered:

- F1: the radio group now has arrow keys and one Tab stop (`ui/radioGroupKeys.js`). The three
  other groups built the same way (theme scope, AI creativity, draft or live) had the same
  fault and got the same fix.
- G1, G2, G3: the review's checks are in the normal suites.
- This note wrongly implied a Firefox check of the frame rule: the spec read only the root's
  `color-scheme`. `theme-switch.spec.js` now reads the frame's corner pixel, in both browsers.

## After the second review (`DARK-MODE-STAGE-02-REVIEW-2026-11-03.md`)

All three findings reproduced, and are fixed:

- S2-F1: an arrow key in the Draft or Live group also moved the selected block, which changed
  the draft. The editor's shortcut handler now leaves a key a control already took. The tab row
  of the Properties panel had the same leak before any of this work, and is fixed by the same line.
- S2-F2: a link to another site under `/s/` got this site's choice, and the server kept it as the
  other site's for a year. The runtime now stops at `/s/<slug>/`. Documents already live keep their
  old runtime until they are sent again, and the server cannot tell such a link from a chosen one.
- S2-F3: the head script and the server read an encoded or repeated parameter differently. Both now
  decode and take the first value. Old head scripts still differ, for addresses nothing generates.

The review's storage-over-cookie gap is in the normal suite as well.
